1. DESCRIPCIÓN GENERAL
================================================================================

Proyecto e-commerce FINALIZADO y en producción, con backend desarrollado en FastAPI,
PostgreSQL como motor de base de datos y un frontend estático en HTML, CSS y
JavaScript vanilla. La plataforma permite gestionar usuarios, catálogo de productos,
categorías, carrito, pagos, checkout invitado, contenido visual de la tienda,
páginas de producto personalizadas, ajustes de configuración, métricas de negocio
y una experiencia de compra más completa para clientes y administradores.

Estado actual: Tienda finalizada y operando en producción en velonox.co. Todos los
módulos principales están completos y estables.
- Infraestructura (migrada en noviembre 2026): backend en Render (plan gratis),
  base de datos PostgreSQL en Neon (plan gratis), frontend en Cloudflare Pages.
  Railway se dio de baja por costo. La base de Neon arrancó vacía (en Railway
  solo había productos de prueba), así que el catálogo real se está cargando
  desde el panel admin.
- Backend: funcional y en uso para la experiencia comercial principal
- Frontend público: funcional y alineado con la experiencia de compra
- Panel de administración: operativo para gestión de productos, layout y ajustes
- Integraciones externas: activas para pagos (Bold), fulfillment (Dropi), TRM y IA
- Widget de chat (n8n): desactivado temporalmente, porque su instancia de n8n
  también vivía en Railway
- Testing automatizado: suite de pytest en backend/tests/, ~95% de cobertura
  (auth, productos, categorías, carrito, pagos, checkout invitado, layout/CMS
  y métricas/ajustes; corre contra SQLite en memoria, sin tocar la base real
  ni servicios externos)

El proyecto salió de la etapa de desarrollo de funcionalidades base. De aquí en
adelante, el trabajo sobre el repositorio consiste en nuevas implementaciones
puntuales y corrección de bugs detectados en producción, no en construir el MVP.

3. ARQUITECTURA TÉCNICA
================================================================================

3.1 BACKEND - FastAPI + PostgreSQL
------------------------------------

El backend está organizado con un enfoque modular, separando rutas, modelos,
esquemas, middleware y servicios.

BASE DE DATOS:
- users: usuarios, autenticación y roles
- products: catálogo de productos
- categories: categorías de productos y navegación comercial
- carts y cart_items: carrito de compras por usuario
- orders y order_items: órdenes y detalle de compra
- store_layout: bloques dinámicos del layout de la tienda
- store_layout_history: snapshot del estado anterior al guardar cambios
- product_pages: contenido enriquecido de páginas de producto
- store_settings: configuraciones generales de la tienda y parámetros comerciales
- product_variants: variantes por producto (nombre, precio opcional, stock, imagen)
- product_images: galería de imágenes por producto (orden, imagen principal)
- password_reset_tokens: tokens de recuperación de contraseña

PRINCIPALES FUNCIONALIDADES BACKEND:
- Rutas de autenticación y perfil de usuario
- CRUD de productos con control de acceso para administradores
- Gestión de categorías y productos por categoría
- Gestión de carrito con validación de stock
- Creación de órdenes y flujo de checkout
- Checkout invitado con creación automática de cuenta y envío de correos
- Confirmación de pagos y actualización del estado de órdenes vía webhooks de Bold
- Gestión de bloques del layout con persistencia en base de datos y versión histórica
- Endpoints para generación de contenido con IA
- Endpoints dinámicos para personalizar páginas de producto
- Endpoints de métricas para seguimiento del negocio
- Endpoints de configuración de la tienda, colores, logo, slogan y TRM
- Rate limiting por IP (slowapi) en endpoints de autenticación y checkout, y
  logging de intentos de login fallidos y rechazos de acceso admin

SERVICIOS Y CAPAS:
- Auth service: registro, login y generación de tokens JWT
- Middleware: protección de rutas por usuario y por administrador
- Schemas: validación y serialización de datos
- Models: estructura relacional del negocio
- Services: envío de correos, pagos con Bold, fulfillment con Dropi y lógica de negocio asociada

3.2 FRONTEND - HTML/CSS/JavaScript
------------------------------------

El frontend está implementado con HTML semántico, estilos propios y JavaScript
vanilla para interactuar con la API.

PÁGINAS IMPLEMENTADAS:
- index.html: home de la tienda y catálogo destacado
- catalogo.html: catálogo completo con búsqueda, filtros y orden
- categoria.html: vista de una categoría específica (requiere ?cat=<slug>)
- categorias.html: listado de categorías disponibles
- login.html: registro e inicio de sesión (incluye login social con Google)
- forgot-password.html y reset-password.html: recuperación de contraseña
- cart.html: visualización y gestión del carrito
- checkout.html: flujo de compra y confirmación de pago
- pedido-confirmado.html: confirmación de pedido tras el pago/checkout
- admin.html: panel administrativo y editor visual
- product.html: detalle de producto con galería, variantes, descripción,
  características y productos relacionados
- nosotros.html: información institucional y propuesta de valor
- contacto.html: formulario de contacto y canal de comunicación
- politicas.html y terminos.html: información legal y condiciones de uso
- sets.html: página temática de contenido comercial (regalos.html se eliminó, ver
  Novedades recientes)
- 404.html: página de error no encontrado

COMPONENTES DESTACADOS:
- Diseño responsive y estilos compartidos
- Integración con la API para carga dinámica de datos
- Persistencia de sesión con token de acceso
- Menú administrativo con vistas de productos, categorías, layout, métricas y ajustes
- Experiencia visual refinada en la página de producto y el editor de layout
- Carga rápida de páginas: peticiones en paralelo, caché local de la última
  versión de cada página y esqueleto animado en la primera visita
- Widget de chat (asistente virtual) con sesión de visitante persistida en el
  navegador -desactivado temporalmente desde noviembre 2026-

4.4 NOVEDADES RECIENTES
------------------------------------
Con la tienda finalizada y en producción, esta sección funciona como changelog:
nuevas implementaciones y corrección de bugs encontrados sobre la marcha, no
desarrollo de funcionalidades base.

- MIGRACIÓN DE INFRAESTRUCTURA (noviembre 2026). Railway se dio de baja por
  costo (estaba cobrando más de lo normal y el sitio quedó caído al no pagar el
  plan). Como en Railway solo había productos de prueba, no se migraron datos:
  se arrancó con una base nueva.
  - Backend -> Render, Web Service plan Free (https://velonox.onrender.com),
    con despliegue automático desde GitHub (main). Se descartaron Google Cloud
    Run (no aceptó el medio de pago para la cuenta de facturación), Fly.io y
    Oracle Cloud (piden tarjeta), Vercel (su plan gratis prohíbe uso
    comercial) y PythonAnywhere (el plan gratis bloquea llamadas a APIs
    externas como Bold y Resend).
  - El plan gratis de Render duerme el servicio tras 15 minutos sin tráfico
    (despertar tarda 30-50 s). Se resolvió con un cron externo
    (cron-job.org) que hace GET a /health cada 10 minutos; las 750 horas
    gratis al mes alcanzan para un servicio encendido 24/7.
  - Base de datos -> Neon, plan Free, connection string "pooled". Se eligió
    sobre Supabase porque Supabase pausa todo el proyecto tras 7 días sin
    actividad y hay que reactivarlo a mano, mientras que Neon solo suspende
    la base y despierta sola en menos de 1 segundo. Se agregó
    pool_pre_ping=True (y pool_recycle) en database.py, porque Neon cierra las
    conexiones inactivas al suspenderse. De paso se limpió database.py, que
    tenía todo su contenido duplicado (engine y Base definidos dos veces).
  - BUG REAL ENCONTRADO: la cadena de migraciones de Alembic no podía
    construir una base vacía. Las tablas categories y product_pages, y varias
    columnas de orders (customer_phone, department_name, city_name,
    bold_order_id, etc.), se habían creado a mano en la base de Railway y
    nunca quedaron en ninguna migración. Por eso "alembic upgrade head" fallaba
    en Neon (ALTER TABLE categories ... sobre una tabla que no existía). Se
    agregó backend/init_db.py, que es el nuevo comando de arranque: si la base
    no tiene la tabla alembic_version (base nueva), crea todo el esquema desde
    los modelos con Base.metadata.create_all() y la marca con "alembic stamp
    head"; si la base ya existe, corre "alembic upgrade head" como siempre, así
    que las migraciones futuras siguen funcionando igual. Se verificó contra
    un Postgres 16 vacío en Docker con Python 3.11: crea las 15 tablas, el
    segundo arranque detecta la base existente, "alembic check" no encuentra
    diferencias entre modelos y esquema, y los 157 tests pasan.
  - Se reemplazó la URL del backend en los 8 archivos del frontend que la
    tenían fija (js/api.js, index, catalogo, categoria, categorias, product,
    sets y admin) y se actualizó la URL del webhook en el panel de Bold
    (https://velonox.onrender.com/payments/bold/webhook).
  - El widget de chat se desactivó: se quitó su <script> de las 10 páginas
    que lo cargaban, porque la instancia de n8n a la que llama también vivía en
    Railway. El archivo js/velonox-chat-widget.js se conserva.
- RENDIMIENTO DE CARGA (noviembre 2026). Síntoma: las páginas tardaban en
  cargar y mientras tanto solo se veía el header sobre un fondo blanco. Causa:
  Render gratis tarda ~0.5 s por petición (incluso /health, que no toca la
  base) y las páginas encadenaban 4-5 peticiones en fila (TRM -> usuario ->
  layout -> productos), más un preflight CORS extra en cada GET. Cambios:
  - apiFetch() solo envía Content-Type cuando la petición lleva body. En un
    GET convertía la petición en "no simple" y forzaba un preflight CORS.
  - getMe() del nav ya no se espera antes de cargar el contenido en ninguna
    página: corre en paralelo.
  - index, catalogo, categoria, categorias, sets y product piden todo en
    paralelo. Para los datos que se pintan después de los bloques del CMS (las
    grillas viven dentro de bloques custom_html) se agregaron
    vxPrefetch(url) / vxTakePrefetched(url) en js/api.js: la petición sale de
    inmediato y la respuesta se consume después.
  - index.html y page-blocks.js guardan en localStorage la última versión de
    los bloques y productos de cada página, la pintan al instante en la
    siguiente visita y solo vuelven a pintar si el backend devuelve algo
    distinto. La TRM también se guarda, para poder mostrar precios antes de que
    responda /settings/trm.
  - Esqueleto animado en el home durante la primera visita, en lugar del
    fondo blanco.
  - Medido en navegador contra el backend real: home de ~2-3 s a ~1 s en la
    primera visita y ~0.1 s en visitas repetidas; catálogo de ~1.3 s a ~0.7 s.
    cart.html y checkout.html siguen esperando la TRM fresca a propósito, para
    que el total mostrado coincida con lo que cobra Bold.
- ORDEN DEL REPOSITORIO (noviembre 2026). Se agregó .gitattributes para
  guardar todo el repo con saltos de línea LF. Editar en Windows dejaba ~50
  archivos marcados como modificados sin ningún cambio real; se verificó que
  ninguno tenía cambios de contenido antes de normalizarlos. Se sacó

  agregó al .gitignore. backend/.env.example ahora incluye RESEND_API_KEY y
  GOOGLE_CLIENT_ID, que faltaban, y marca las variables SMTP como obsoletas.

- Incidente real y corregido: al correr esa migración contra producción

- Se eliminó frontend/regalos.html junto con todos sus enlaces de navegación

- Se integró Google Analytics (gtag.js, ID G-J3ENJRV492) en las 19 páginas
  HTML del frontend, insertando el script justo después de <head> en cada una.
- Corrección de bug real: el script de Cloudflare Web Analytics se cargaba
  con type='module' en vez de defer (el snippet oficial de Cloudflare usa
  defer). Al ser un script cross-origin cargado como módulo ES, el navegador
  fuerza un fetch en modo CORS y aplica comprobaciones de seguridad de
  módulos, lo que generaba en consola errores de CORS y de integridad (SRI)
  -sin que existiera ningún atributo integrity real en el HTML- en varias
  páginas (index.html, cart.html, admin.html, terminos.html, nosotros.html,
  product.html, contacto.html y politicas.html). Se verificó contra el HTML
  servido en producción (velonox.co) y el historial completo de git antes de
  corregir, confirmando que nunca existió un atributo integrity/crossorigin;
  se corrigió el atributo a defer en las 8 páginas afectadas.
- Auditoría de seguridad rápida del backend (agosto 19-20, 2026) y set de
  correcciones aplicado sobre los hallazgos, en commits separados y
  verificados uno por uno:
  - Rate limiting con la librería slowapi en los endpoints más expuestos a
    abuso: /auth/login, /auth/register y /auth/forgot-password (5/minuto),
    /guest/checkout (5/minuto) y /payments/checkout (10/minuto). La IP real
    del cliente se identifica vía el header X-Forwarded-For, ya que el hosting
    (Railway en ese momento, hoy Render) corre el backend detrás de un
    proxy (get_remote_address por sí solo
    devolvía la IP del proxy, no la del cliente). El webhook
    /payments/bold/webhook queda deliberadamente sin límite, porque lo llama
    la pasarela de pago, no un usuario final.
  - Se agregó logging.basicConfig() global en main.py (el proyecto no tenía
    ninguna configuración de logging antes de esto) y se agregó logging en
    nivel WARNING para intentos de login fallidos (con el email, nunca la
    contraseña) y para rechazos de autorización admin/token inválido (con
    user_id/email y la IP), sin cambiar ningún status code ni mensaje de
    error visible para el cliente. Pensado para poder detectar fuerza bruta
    o intentos de escalar privilegios revisando los logs del hosting (hoy,
    Render -> servicio -> Logs).
  - Corrección de una fuga de enumeración de usuarios en POST /auth/register:
    el mensaje de error cuando el email ya existía revelaba explícitamente
    que la cuenta estaba registrada. Se reemplazó por un mensaje genérico,
    mismo patrón que ya usaba correctamente /auth/forgot-password, sin
    cambiar el status code (400) ni el resto del flujo de registro.
  - Corrección de una fuga de enumeración de usuarios en POST
    /guest/checkout: la respuesta ya no incluye el campo que revelaba si el
    email ingresado correspondía a una cuenta existente. Además, un checkout
    de invitado con el email de una cuenta ya registrada ya no asocia la
    orden a esa cuenta real sin verificar que quien hace el checkout es su
    dueño -antes cualquiera podía "ensuciar" el historial de pedidos de una
    cuenta ajena solo conociendo su email-; ahora la orden queda anónima
    (user_id NULL).
  - Migración de Alembic (8d33da579547) para permitir orders.user_id nulo,
    requisito del fix anterior: la tabla orders en Postgres tenía esa
    columna como NOT NULL desde la migración inicial del proyecto
    (ff0162fd9e2e), aunque el modelo SQLAlchemy (models/order.py) ya la
    declaraba nullable=True desde antes -un desfase entre el modelo y el
    esquema real que nunca se había detectado-. Se generó la migración, se
    aplicó primero en la base de datos local para verificar el fix contra
    Postgres real (no solo contra el SQLite en memoria de los tests) y
    finalmente se desplegó a producción junto con el resto de estos commits.
  - Todo el trabajo se verificó manualmente en cada paso contra un servidor
    local (no solo con la suite de pytest): login válido/inválido, registro
    con email nuevo/duplicado, checkout invitado con email nuevo/existente,
    checkout autenticado, el webhook de Bold con firma válida, y una prueba
    explícita de 6 intentos rápidos de login confirmando el 429 en el sexto
    sin afectar el uso normal de un solo usuario.


5. INFRAESTRUCTURA DEL PROYECTO
================================================================================

5.1 ARQUITECTURA DE INFRAESTRUCTURA
------------------------------------

El proyecto está compuesto por tres capas principales:
- Capa de frontend: archivos estáticos HTML/CSS/JS servidos desde Cloudflare Pages
  (velonox.co).
- Capa de backend: API REST desarrollada con FastAPI y ejecutada mediante Uvicorn,
  alojada en Render (https://velonox.onrender.com).
- Capa de datos: base de datos PostgreSQL en Neon, servicio independiente del
  hosting del backend.

La comunicación entre el frontend y el backend se realiza mediante peticiones HTTP
seguras, con autenticación por token JWT y configuración de CORS para permitir el
acceso desde entornos locales y de despliegue.

5.2 COMPONENTES DE DESPLIEGUE
------------------------------------

Backend (Render, Web Service plan Free):
- Ejecutado con Uvicorn en un entorno ASGI.
- Root directory: backend. Build: pip install -r requirements.txt.
- Arranque: python init_db.py && uvicorn main:app --host 0.0.0.0 --port $PORT.
  El Start Command configurado en el panel de Render tiene prioridad sobre
  backend/procfile, así que ambos deben coincidir.
- Versión de runtime definida en runtime.txt (Python 3.11).
- Despliegue automático en cada push a main.
- Endpoints de salud disponibles en /health y /db-check para verificación básica.
- Un cron externo (cron-job.org) llama a /health cada 10 minutos para que el
  plan gratis no duerma el servicio.

Frontend (Cloudflare Pages):
- Estructurado como sitio estático con archivos HTML, CSS y JS, sin build.
- La URL del backend está fija en el código: API_URL en js/api.js y la
  constante API de cada página HTML. Si el backend cambia de URL, hay que
  actualizar ambos y el webhook en el panel de Bold.

Base de datos (Neon, plan Free):
- PostgreSQL como motor principal, connection string "pooled".
- Modelos relacionales gestionados con SQLAlchemy.
- Migraciones a través de Alembic, aplicadas al arrancar mediante init_db.py
  (ver Novedades recientes: la cadena de migraciones no puede construir una
  base vacía por sí sola).

5.3 VARIABLES Y CONFIGURACIÓN
------------------------------------

La aplicación depende de variables de entorno para su funcionamiento en distintos
eventos. Entre las más importantes se encuentran:
- DATABASE_URL: conexión a la base de datos PostgreSQL (Neon, "pooled")
- SECRET_KEY, ALGORITHM y ACCESS_TOKEN_EXPIRE_MINUTES: firma y duración de JWT
- FRONTEND_URL: URL base del frontend, usada en los links de los correos
- BOLD_API_KEY y BOLD_SECRET_KEY: acceso a la API de Bold y verificación de
  integridad. Deben ser las mismas (y del mismo modo, pruebas o producción)
  que las del panel de Bold donde está configurado el webhook; si no, los
  webhooks se rechazan y los pedidos se quedan en "pending".
- DROPI_BASE_URL y DROPI_API_KEY: integración con Dropi (vacías por ahora)
- ANTHROPIC_API_KEY: acceso a la integración de IA
- RESEND_API_KEY y EMAILS_FROM: envío de correos transaccionales vía Resend
- GOOGLE_CLIENT_ID: login con Google
- SMTP_*: ya no se usan (se migró a Resend porque los hostings bloquean los
  puertos SMTP salientes)

La plantilla está en backend/.env.example. En local se usa backend/.env
(ignorado por git); en producción se configuran en el panel de Render. Estas
variables no deben exponerse en el código ni en archivos compartidos.

5.4 SEGURIDAD E INFRAESTRUCTURA
------------------------------------

La infraestructura actual contempla:
- Protección de endpoints con middleware de autenticación y autorización
- Tokens JWT para sesiones de usuario y administración
- CORS habilitado para orígenes permitidos
- Gestión de secretos vía variables de entorno
- Integración con webhooks para confirmación de pagos de forma asíncrona
- Separación de roles entre usuarios y administradores
- Rate limiting por IP (slowapi) en endpoints de login, registro,
  recuperación de contraseña y checkout, para mitigar fuerza bruta y abuso
- Logging de intentos de login fallidos y rechazos de autorización admin,
  con IP del cliente, para poder detectar patrones de ataque en los logs
- Mensajes de error genéricos en registro y checkout invitado para no
  permitir enumerar qué emails están registrados en la tienda

5.5 ESTADO DE LA INFRAESTRUCTURA
------------------------------------

La infraestructura del proyecto está desplegada y operando en producción sin
costo de hosting: el backend corre como Web Service gratis en Render, la base de
datos PostgreSQL en Neon (gratis) y el frontend como contenido estático en
Cloudflare Pages.

Límites conocidos del plan gratis:
- Cada petición al backend tarda ~0.5 s (latencia del plan). El frontend se
  optimizó para compensarlo (ver Novedades recientes), pero bajarla requiere
  un plan pago.
- Render duerme el servicio sin tráfico; se mitiga con el cron a /health. Si
  el cron falla, la primera visita después de 15 minutos tarda 30-50 s.
- 512 MB de RAM y CPU compartida: suficiente para el volumen actual.

Posibles mejoras futuras, a implementar solo si surge la necesidad (no bloquean
la operación actual de la tienda):
- Subdominio propio para la API (api.velonox.co) mapeado a Render, para que un
  futuro cambio de proveedor solo requiera tocar el DNS en Cloudflare
- Volver a alojar n8n para reactivar el widget de chat
- CI/CD que corra la suite de pytest antes de desplegar
- ambientes de staging y producción separados
- monitoreo y logs más completos

7. MAPA ESTRUCTURAL DEL PROYECTO PARA IA Y MANTENIMIENTO
================================================================================

Este proyecto está organizado como una aplicación web full-stack con una separación
clara entre frontend, backend, base de datos y documentación. La idea general es que
el frontend entregue una experiencia comercial y visual al usuario, mientras el
backend centraliza la lógica de negocio, seguridad, autenticación, pagos, layout y
persistencia.

7.1 ESTRUCTURA GENERAL DEL REPOSITORIO
------------------------------------

- backend/: corazón del sistema. Aquí viven los modelos de datos, rutas API,
  esquemas, servicios, middleware y la entrada principal de la aplicación.
- frontend/: sitio estático que representa la experiencia visible del cliente y del
  administrador. Aquí se encuentra el catálogo, carrito, checkout, páginas
  institucionales y el panel admin.
- docs/: documentación técnica y de negocio. Aquí se concentran notas de proyecto,
  arquitectura y referencias operativas.
- alembic/: migraciones de base de datos para mantener el esquema SQLAlchemy
  alineado con PostgreSQL.
- package.json: configuración mínima de dependencias frontend. node_modules/ no
  se versiona (está en .gitignore); el sitio no lo usa, motion se carga desde CDN.
- .gitattributes: normaliza los saltos de línea del repo a LF, para que editar
  en Windows no marque archivos como modificados sin cambios reales.

7.2 MAPA DEL BACKEND
------------------------------------

El backend está construido sobre FastAPI y SQLAlchemy, con una organización modular:

- backend/main.py
  Punto de entrada de la aplicación. Aquí se crea la instancia de FastAPI, se
  configura logging global (logging.basicConfig), se instancia el Limiter de
  slowapi (identifica al cliente por IP real vía X-Forwarded-For) y se
  registran su handler de error 429 y su middleware, se configuran los
  middlewares de CORS, se registran los routers principales (importados
  después del Limiter, ya que varios routers hacen "from main import
  limiter" para decorar sus endpoints con @limiter.limit(...)) y se exponen
  endpoints de salud como /health y /db-check.

- backend/database.py
  Define la conexión a PostgreSQL (con pool_pre_ping para Neon), la sesión de
  base de datos y el patrón de inyección de dependencias que usan las rutas.

- backend/init_db.py
  Se ejecuta en cada arranque, antes de uvicorn. En una base nueva crea el
  esquema desde los modelos y hace "alembic stamp head"; en una base existente
  corre "alembic upgrade head". Existe porque la cadena de migraciones no puede
  construir una base vacía desde cero.

- backend/models/
  Contiene los modelos ORM que representan las tablas del negocio. Los modelos más
  importantes son:
  - user.py: usuarios, autenticación y rol de administrador
  - product.py: catálogo de productos y stock
  - category.py: categorías de productos
  - cart.py: carritos y items del carrito
  - order.py: órdenes y detalle de compra
  - layout.py: bloques del editor visual de la tienda
  - product_page.py: contenido enriquecido de páginas de producto
  - settings.py: parámetros de configuración de la tienda

- backend/schemas/
  Define los modelos Pydantic usados para validar y serializar los datos de entrada
  y salida de la API. Cada dominio tiene su propio esquema: user.py, product.py,
  cart.py, order.py, layout.py, category.py, product_page.py.

- backend/routes/
  Agrupa los endpoints HTTP del sistema. Cada archivo representa un dominio
  funcional:
  - auth.py: registro, login y datos del usuario autenticado
  - products.py: CRUD de productos
  - categories.py: categorías y productos por categoría
  - cart.py: agregar, actualizar y eliminar productos del carrito
  - payments.py: checkout con Bold, webhook y fulfillment
  - guest_checkout.py: flujo de compra para usuarios no registrados
  - layout.py: editor visual del layout, historial y generación de bloques con IA
  - product_pages.py: páginas de producto personalizadas
  - metrics.py: métricas de negocio para el panel admin
  - settings.py: ajustes de tienda, colores, banner, slogan y TRM

- backend/services/
  Contiene lógica de negocio transversal que no pertenece directamente a una ruta:
  - auth.py: hash de contraseñas, autenticación y generación de tokens JWT
  - bold.py: firma de integridad y verificación de webhooks de Bold
  - dropi.py: creación de órdenes de envío con Dropi
  - email.py: envío de correos transaccionales y confirmaciones
  - settings.py: cálculo y acceso a la TRM

- backend/middleware/
  - auth.py: middleware y dependencias para verificar JWT y roles de
    usuario/admin (get_current_user, get_current_admin); loguea en WARNING
    los tokens inválidos/expirados y los rechazos por falta de rol admin,
    con la IP del cliente

- backend/alembic/
  Mantiene las migraciones SQL para crear y modificar tablas en PostgreSQL. Es
  fundamental para despliegues y para mantener el estado del esquema alineado.
  Importante: las migraciones solo sirven para evolucionar una base que ya
  existe. Para una base vacía, usar "python init_db.py", no "alembic upgrade
  head" directo.

7.3 MAPA DEL FRONTEND
------------------------------------

El frontend es estático y está compuesto por archivos HTML, CSS y JavaScript vanilla.
La idea es que el navegador consuma la API del backend directamente, sin depender de
un framework complejo.

- frontend/index.html
  Página de inicio y catálogo principal.

- frontend/product.html
  Pantalla de detalle del producto con descripción, características y productos
  relacionados.

- frontend/cart.html
  Carrito de compras con interacción para modificar cantidades y eliminar ítems.

- frontend/checkout.html
  Flujo de compra y visualización del estado del pedido.

- frontend/login.html
  Registro e inicio de sesión para clientes y administradores.

- frontend/admin.html
  Panel administrativo principal. Aquí se concentra la edición visual del layout,
  la administración de productos, métricas y ajustes del negocio.

- frontend/categorias.html, sets.html, nosotros.html,
  contacto.html, politicas.html, terminos.html
  Páginas informativas y temáticas que complementan la experiencia comercial
  (regalos.html se eliminó, ver Novedades recientes).

- frontend/css/styles.css
  Estilos globales de la tienda.

- frontend/js/api.js
  Centraliza la comunicación con la API. Aquí se define el manejo base de peticiones,
  headers, autenticación, moneda y endpoints. También contiene los helpers de
  rendimiento: vxCacheGet/vxCacheSet (caché en localStorage del contenido de
  cada página), vxPrefetch/vxTakePrefetched (lanzar un GET temprano y usar su

- frontend/js/auth.js
  Lógica de sesión, registro, login y protección de vistas.

- frontend/js/cart.js
  Interacción con el carrito desde la interfaz.

- frontend/js/page-blocks.js
  Lógica del editor visual del layout, bloques dinámicos y administración de

- frontend/js/motion.js
  Animaciones y mejoras de experiencia visual.

- frontend/js/velonox-chat-widget.js
  Widget de chat auto-inicializable y sin dependencias. Se activa agregando
  un <script> antes de </body> en la página; envía los mensajes directamente
  a un webhook externo de n8n (no pasa por el backend de Velonox) y guarda un
  identificador de sesión de visitante en localStorage. DESACTIVADO desde
  noviembre 2026: ninguna página lo carga, porque su n8n estaba en Railway.

7.4 FUNCIONES Y FLUJOS IMPORTANTES DEL NEGOCIO
------------------------------------

El proyecto sigue un patrón claro de flujo de negocio que una IA debe entender para
realizar cambios seguros:

1. Autenticación
   - El frontend envía email y contraseña a /auth/login.
   - El backend valida las credenciales, genera un token JWT y lo devuelve.
   - El token se guarda en el cliente y se usa en rutas protegidas.

2. Catálogo y productos
   - /products/ lista productos activos.
   - /products/{id} devuelve detalle de un producto.
   - /categories/ organiza productos por categoría.

3. Carrito
   - /cart/ devuelve el carrito del usuario autenticado.
   - /cart/items permite agregar, actualizar o eliminar productos.
   - La lógica valida stock antes de registrar cambios.

4. Checkout y pagos
   - /payments/checkout crea una orden y prepara el flujo de pago según el método elegido.
   - /payments/checkout admite pago anticipado (Bold) y contraentrega (confirmación inmediata + Dropi).
   - /payments/bold/webhook actualiza el estado de la orden y descuenta stock al confirmar el pago.

5. Checkout invitado
   - /guest/checkout permite crear un pedido sin crear una cuenta previa.
   - El flujo crea automáticamente un usuario temporal, genera la orden y envía
     correos de bienvenida y confirmación.

6. Layout y edición visual
   - /layout/ y /layout/history permiten guardar, restaurar y resetear bloques CMS.
   - /layout/generate-block genera bloques de contenido con IA.
   - El frontend admin usa estos endpoints para previsualizar cambios en tiempo real.

7. Ajustes y métricas
   - /settings/ administra branding, colores, banner, configuración comercial y TRM.
7.5 PUNTOS DE EXTENSIÓN RECOMENDADOS
------------------------------------

Para futuras mejoras o para que una IA trabaje sobre el proyecto sin romperlo, los
puntos más sensibles y recomendables para modificar con cuidado son:

- backend/models/: si se agregan nuevas tablas o columnas, deben reflejarse también
  en Alembic y en los schemas correspondientes.
- backend/routes/: cualquier cambio en endpoints debe ir acompañado de su consumo
  en frontend/js/api.js y en las vistas HTML correspondientes.
- backend/middleware/auth.py: si se cambian permisos o roles, deben revisarse todas
  las rutas protegidas.
- frontend/js/page-blocks.js: el editor visual depende de este archivo para renderizar
  bloques y manejar la experiencia de administración.
- frontend/js/api.js: cualquier cambio en la forma de llamar a la API debe integrarse
  aquí para evitar inconsistencias.
- Rendimiento: con ~0.5 s por petición, nunca encadenar con await peticiones
  que no dependen entre sí. Usar Promise.all o vxPrefetch, y no esperar a
  getMe() antes de cargar el contenido.
- frontend/index.html: el elemento <div id="layout-container"></div> debe
  quedar exactamente así, porque admin.html lo busca y reemplaza como texto
  para armar la vista previa del editor.

7.6 CONVENCIÓN DE DESARROLLO RELEVANTE
------------------------------------

- El proyecto usa SQLAlchemy en modo síncrono, no async ORM.
- Se prefieren cambios pequeños y explícitos sobre archivos existentes.
- Los secretos y credenciales deben mantenerse en variables de entorno y nunca
  hardcodeadas.
- La separación entre rutas, modelos, esquemas y servicios debe mantenerse para
  facilitar el mantenimiento y la comprensión por parte de herramientas de IA.
